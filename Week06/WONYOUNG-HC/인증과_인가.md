## 인증과 인가의 개념

### 인증 (Authentication)

- 어떤 사실 또는 어떤 문서가 진짜인지 증명하는 과정을 가리키는 용어
- 어떤 개체의 신원을 확인하는 과정
- 사용자의 신원을 검증하는 프로세스
- 아이디와 비밀번호를 통해 로그인을 하는 행위
- 유저가 누구인지 확인하는 절차

### 인가 (Authorization)

- 엔티티가 엑세스할 수 있는 리소스 또는 수행할 수 있는 작업
- 어떤 개체가 어떤 리소스에 접근할 수 있는지 또는 어떤 동작을 수행할 수 있는지를 검증
- 인증된 사용자가 어떠한 자원에 접근할 수 있는지를 확인하는 절차
- 유저에 대한 권한을 허락하는 것
- 인증된 사용자에 대한 자원 접근 권한 확인
- 자원을 적절한/유효한 사용자에게 전달/공개 하기 위한 방법

### 웹에서 인증과 인가

인증 : 사용자가 **로그인**을 통해 신원을 확인
<br>
인가 : 서버가 인증된 사용자에게 신원에 맞는 **서비스를 제공**

<br>

## 기본 인증 방식

### 기본 인증 방식의 동작

<img src="https://docs.oracle.com/cd/E19159-01/819-3669/images/security-httpBasicAuthentication.gif">

- 클라이언트가 사용자의 정보를 **HTTP header**에 담아 보냄
- 사용자의 정보를 base4로 인코딩하여 서버에게 전송
  - `Authorization: Basic base64({username}:{password})`

### 클라이언트가 인증 정보를 저장하는 방법

<img src="https://miro.medium.com/v2/resize:fit:537/1*_njX4rWrMoYhgIbF6Piprg.jpeg">

- 클라이언트가 인가된 요청을 받기 위해 서버에게 아이디와 비밀번호로 이루어진 인증 코드를 전송해야 함
- HHTP는 stateless한 특징을 가지고 있기 때문에 클라이언트와 서버가 이전에 통신한 내역을 참조할 수 없음
- 즉 인증 코드를 저장하고 있지 않다면 클라이언트는 인가된 요청을 보낼때 마다 사용자에게 로그인을 요구해야 함
- 이러한 문제를 해결하기위해 클라이언트는 **web storage** 또는 **cookie**를 통해 로그인 이후 인증 코드를 저장해 둠

### 기본 인증 방식의 장단점

#### 장점

- 구현이 쉬움

#### 단점

- request header에 사용자의 개인 정보가 포함되어 있어 보안에 취약함

<br>

## 세션 인증 방식

### 세션 인증 방식의 동작

<img src="https://miro.medium.com/v2/resize:fit:1400/1*Hg1gUTXN5E3Nrku0jWCRow.png">

- 사용자가 로그인을하면 클라이언트는 서버에게 아이디와 비밀번호를 통해 인증을 시도
- 사용자의 아이디와 비밀번호가 일치하면 서버는 `session ID`와 `사용자 정보`가 key-value로 이루어진 **세션 테이블**을 생성
- 서버는 로그인의 응답으로 사용자에게 `session ID`를 전송
- 클라이언트는 **session ID**를 `web storage` 또는 `cookie`에 저장하여 인가된 요청을 보낼 때 마다 **session ID**를 **인증 정보**로 전송
- 서버는 세션 테이블에 `session ID`가 존재하면 인가된 요청을 허가

### 세션 인증 방식의 장단점

#### 장점

- 클라이언트는 인증 정보로 사용자 개인정보와 아무 관련이 없는 `session ID`만을 인증 정보로 가지기 때문에 사용자 개인 정보 유출이 없음
- `session ID`가 탈취 당해도 서버는 세션 테이블에서 해당 `sessoin ID`를 삭제시켜 탈취당한 인증 정보를 사용하지 못하게 할 수 있음

#### 단점

<img src="https://www.netscaler.com/content/dam/netscaler/images/graphics/infographics/what-is-load-balancing.png">

- 서버의 규모가 커져 로드 밸런싱을 통해 여러 서버를 구축하는 경우 **일관성** 문제가 발생
- 최초 로그인 요청은 1번 서버에게 전송되면, 사용자의 `session ID`는 **1번 서버 세션 테이블**에 저장
- 사용자가 다음 인가된 요청이 3번 서버에게 전성되면, **3번 서버에는 사용자의 인증 정보가 존재하지 않음**
- 사용자 입장에서는 로그인을 했지만, 서버가 계속 바껴 로그인이 유지되지 않는 현상이 발생

<br>

## 토큰 인증 방식

### 토큰 인증 방식의 동작

<img src="https://hudi.blog/static/5429c4ae31c81d5c823b77fedc6c5dcf/1263b/token-based-authentication.png">

- 사용자가 로그인을 하면 클라이언트는 서버에게 아이디와 비밀번호를 통해 인증을 시도
- 사용자의 아이디와 비밀번호가 일치하면 서버는 secret key를 통해 사용자의 정보가 담긴 **토큰**을 생성
- 서버는 로그인의 응답으로 사용자에게 토큰을 전송
- - 클라이언트는 **토큰**을 `web storage` 또는 `cookie`에 저장하여 인가된 요청을 보낼 때 마다 **토큰**을 **인증 정보**로 전송
- 서버는 secret key를 통해 자신이 생성한 토큰임을 확인하면 인가된 요청을 허가

### JWT (Json Web Token)

- 웹에서 사용되는 JSON 형식의 토큰에 대한 표준 규격
- header, payload, signature로 구성
  - header : 토큰의 타입, 암호화 알고리즘
  - payload : 사용자의 정보, 만료 기한
  - signature : 토큰이 변조되었는지 확인
- 토큰은 클라이언트가 보유하고, 서버와 통신간에 사용되기 때문에 탈취 위험이 존재하므로 payload에 사용자의 민감한 정보가 포함되면 안됨

### 토큰 인증 방식의 장점과 단점

#### 장점

- 서버는 사용자의 정보를 저장하지 않아 서버의 부담이 적음

#### 단점

- 토큰에 개인 정보가 포함되어 있기 때문에 개인 정보 노출이 어느정도 발생
- 토큰이 탈취당한 경우 서버는 토큰에 대한 정보를 저장하지 않기 떄문에 **만료 기한**이 지나기 전까지는 **탈취된 토큰으로 인가된 요청이 허가됨**

### Refresh Token

- 탈취된 토큰으로 인가된 요청이 가능한 토큰 인증 방식의 단점을 보완
- 사용자가 로그인을 하는 경우 서버는 `access token`과 `refresh token` 두 가지의 토큰을 발급하여 **클라이언트에게 전송**하고, **서버는 `resfresh token`만 저장**
- 클라이언트는 인가된 요청을 `access token`을 인증 정보로 이용하지만, `access token`의 만료 기간은 1시간 이내의 **짧은 시간**을 사용
- `acceess token`의 만료 기간이 지난 경우 클라이언트는 `refresh token`을 통해 `access token` **재 발급 요청**을 전송
- 서버는 재 발급 요청에 대해 자신이 발급한 `refresh token`이 맞는지 확인되면 **새로운 `access token`을 발급**
- 서버에 부담이 적은 토큰 인증 방식과, 보안성이 높은 세션 인증 방식을 접목시킨 방식
- 단 토큰에 있는 개인 정보는 여전히 노출 가능하고, `access token`이 만료 되기 전까지는 사용 가능하다는 문제는 존재

### Session ID vs Refresh Token

- session ID와 refresh token 둘 다 서버에 저장하지만, refresh token을 사용하는 것이 세션 테이블을 사용하는 것보다 효율적인 이유는 **참조 횟수**임
- 세션 인증 방식에서 session ID는 **인가된 요청을 전송할 때 마다** 세션 테이블을 계속 확인하기 때문에 서버에 부담이 증가
- 토큰 인증 방식에서 refresh token은 acceess token이 만료된 경우 **토큰 재 발급 요청에만** 저장한 refresh token을 확인하기 떄문에 서버의 부담이 세션 인증 방식보다는 적음

<br>

## 소셜 로그인

### OAuth

- 인터넷 사용자들이 비밀번호를 제공하지 않고 다른 웹사이트 상의 자신들의 정보에 대해 웹사이트나 애플리케이션의 접근 권한을 부여할 수 있는 공통적인 수단으로서 사용되는, 접근 위임을 위한 개방형 표준
- 서버가 사용자의 개인 정보를 저장하지 않고, **다른 서비스로 부터 사용자의 개인 정보 열람을 위임 받는 프로토콜**

### OAuth의 동작 방식

용어 정리
<br>
Resource owner : 클라이언트(사용자)
<br>
Client : 서버
<br>
Authorization server, Resource server : 사용자의 개인 정보를 보유하고 있는 다른 웹사이트나 애플리케이션

<img src="https://images.velog.io/images/amuse/post/446f9ac7-3369-4042-8005-7775f3897c6a/security_8.png">

- 사용자가 로그인을 요청하면, 클라이언트는 사용자에게 서버의 로그인 url을 전송
- 사용자는 서버의 url에서 서버 계정을 사용해서 로그인을 하면 서버는 사용자에게 **authentication code**를 전송
- 사용자가 클라이언트에게 **authentication code**를 전송하면, 클라이언트는 서버에게 authentication code를 통해 사용자의 개인 정보를 열람할 수 있는 **access token**을 발급
- 클라이언트는 **access token**을 사용해 서버에 있는 사용자의 개인 정보를 열람

### 소셜 로그인과 OAuth

- OAuth는 **사용자의 개인 정보를 열람**할 수 있는 프로토콜이지, 소셜 로그인을 제공하지 않음
- 소셜 로그인을 제공하기 위해서는 클라이언트가 **OAuth를 사용해 서버로부터 사용자의 개인 정보**를 가져오고, 이를 통해 **인가된 요청을 허가**하는 방식
